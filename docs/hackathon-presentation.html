Consensus on a Hidden Processor

A Cortex-M3 service processor (SCPU) sits on every switch SoC in every box in our platform. We proved it can run distributed Raft consensus for sub-100ms failure detection - adding just 12 KB of code to a core with 126 KB of SRAM, leaving the vast majority of its resources free for future applications.

The Problem

Software monitors die with the node they watch

Traditional cluster HA relies on software-only failure detection running on the same processors being monitored. When a node crashes, its failure monitor dies with it. Detection falls back to remote timeouts - 40+ seconds for k3s/etcd by default.

⚠

Shared failure domain

A kernel panic, OOM kill, or hardware fault takes out both the application and its health monitor simultaneously. The monitor dies with the node it watches.

⏳

Slow detection

k3s default node-monitor-grace-period is 40 seconds. Etcd leader election adds more. Total recovery can exceed 2 minutes.

🔎

Low-fidelity detection

Remote health checks can only say "I can't reach it." They can't distinguish a crashed node from a congested link - leading to false positives and unnecessary failovers.

🛠

Software complexity

Implementing reliable failure detection in software means timeouts, retries, quorum logic, and state machines - all running on the same overloaded host CPUs you're trying to monitor.

The Solution

Raft consensus on the Switch SCPU

Every switch SoC in our platform has independent Cortex-M3 service processor cores (SCPUs) with their own voltage rail, firmware, and Ethernet access. Run a lightweight Raft cluster across these physically isolated cores. They communicate over raw L2 Ethernet - no IP stack, no TCP, just custom EtherType frames at wire speed. Failure detection in under 100ms, consensus-backed.

☍

Isolated failure domain

Separate silicon, separate voltage rail, separate firmware. The monitor physically cannot crash with the host it watches.

⚡

L2 wire-speed detection

Raw Ethernet II frames with custom EtherTypes (0x88B5 Raft, 0x88B6 Health, 0x88B7 Heartbeat). No protocol stack overhead.

⚖

Consensus, not just pings

Raft voting ensures "the majority agrees node X is down" - not just "I can't see it." Eliminates false positives from transient link issues.

⚙

Purely additive

If the oracle fails, k3s falls back to its normal (slower) detection. The oracle is never in the critical path for cluster correctness.

Live Demo

Three boards, one switch, zero configuration

The demo itself is deliberately simple: three dev boards, a switch, and some Ethernet cables. Raft does what Raft is expected to do - nodes elect a leader, detect failures, and recover. The interesting part comes next: how little of the processor this actually costs.

We chose the STM32 Nucleo-F207ZG because it has the exact same ARM Cortex-M3 core embedded in the switch SoC on our production hardware. Same instruction set, same constraints, same class of resources. The production SCPU SDK runs the same RTOS with the same DMA descriptor-ring model for packet I/O - ~3,400 lines of consensus and protocol code transfer unchanged. See the transport parity analysis for the full side-by-side comparison.

Pull a cable - the remaining nodes detect the failure, elect a new leader, and continue operating. Plug it back in - the node rejoins seamlessly.

Four-quadrant view: three serial consoles showing real-time Raft state + camera feed of the physical setup.

The Key Finding

It barely touches the processor

The production SCPU runs entirely from SRAM - there is no flash. Each core has 126 KB of SRAM, and the existing SCPU SDK firmware occupies ~40 KB, leaving ~84 KB free. Everything we add totals just 12 KB: a 5.7 KB Raft library (forked from willemt/raft) plus 6.3 KB of oracle application code. An optimized build drops that further to ~8 KB.

On our STM32 prototype (which has 1 MB flash + 128 KB SRAM), the complete standalone firmware including FreeRTOS, HAL drivers, debug output, and C library fits in 37 KB. But most of that infrastructure already exists on the production service processor - the meaningful number is the 12 KB delta.

Most of the effort was not writing code - it was systems integration, bare-metal porting, and wire protocol design. Proving that something fits required building it and measuring every byte.

Production Projection

What fits on the target service processor

The production target has 4x Cortex-M3 SCPU cores at 650 MHz, 126 KB SRAM per core (384 KB aggregate, 3 cores user-available). The SCPU SDK baseline firmware occupies ~40 KB, leaving ~84 KB free. Our oracle adds just ~13.5 KB - consuming 10.7% of per-core SRAM and leaving ~72 KB free for future applications. Firmware is loaded into SRAM via PCIe BAR mmap from the host - there is no flash on the CM3.

Transport parity: The production SCPU SDK uses the same RTOS and the same DMA descriptor-ring model (SDMA) with identical ownership semantics. The ~400-line STM32 transport becomes a ~300-line SDMA equivalent that uses less code and 93% less buffer SRAM (0.8 KB vs 12.2 KB, because oracle frames are only 88 bytes). The SCPU's 5.4x faster clock and internal backplane eliminate PHY startup delay and improve throughput. See the transport parity analysis for details.

SRAM savings: 29 KB → 1 KB

Right-sizing the Raft log from 1,500 to 32 entries saves 29 KB of heap (32 covers worst-case burst for a 4-box deployment). Transport buffers drop from 12 KB to under 1 KB because oracle frames are 88 bytes, not the full 1500-byte MTU.

✓

Code savings: 12 KB → ~8 KB

Compiler size optimization, stripping printf (4.8 KB) and debug asserts. The oracle delta shrinks from 12 KB to ~8 KB of code.

✓

3 more CM3 cores available

The switch SoC has 4 Cortex-M3 SCPU cores. The oracle needs only one. Three cores remain for additional services - notably, switch configuration services when the host CPU has failed.
